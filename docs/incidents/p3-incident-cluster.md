# P3 Incident Cluster — Performance & Caching

These are issues that caused slow retrieval, stale cached data, redundant
LLM calls, or context-window overflow. Read before touching: conversation
summarization, RAG search, memory-book pipeline, context prompt
construction.

## P3.1 — Conversation-summary prompt_version + schema_version staleness check

**Locations**
- `packages/server/app/services/conversation_memory.py:30`
- `packages/server/app/services/conversation_memory.py:56`
- `packages/server/app/services/conversation_memory.py:156`

**What went wrong**
Conversation summaries had no schema versioning. When the prompt template
or the `ConversationSummaryData` Pydantic shape changed, old rows in the
DB were trusted blindly. A user who'd chatted 200 messages before a
prompt improvement shipped never benefited from the improvement —
their cached summary (generated by the old prompt) kept being returned
forever.

**Why the fix works**
- `MEMORY_SCHEMA_VERSION = 1` bumps when ConversationSummary JSON shape
  gains/loses fields.
- `_build_summary_metadata()` captures `prompt_version + schema_version
  + model + generated_at` alongside each summary.
- `_is_summary_stale()` treats NULL metadata as stale (pre-P3.1 rows)
  and triggers regeneration.
- A stale-version row is force-regenerated even if `message_count` looks
  current — prompt improvements backfill to historical summaries.

**Regression red-flag**
- Adding a field to `ConversationSummaryData` without bumping
  `MEMORY_SCHEMA_VERSION`.
- Changing `CONVERSATION_SUMMARY_SYSTEM.version` without verifying the
  staleness check trips on existing rows.
- Reading summary without going through `get_or_create_summary()` (which
  contains the staleness check).

## P3.2 — Hybrid search via RRF + token-aware daily budget path

**Locations**
- `packages/server/app/config.py:155`
- `packages/server/app/prompts/base.py:13`
- `packages/server/app/services/rag/search.py:16`, `:205`, `:268`
- `packages/server/app/services/companion/context.py:85`
- `packages/server/app/middleware/daily_llm_budget.py:8`

**What went wrong**
Three related failures:
1. **Cascading fallback**: if semantic search returned anything (even
   low-relevance), keyword search never ran. Exact-term matches got
   buried by vague semantic similarity.
2. **Request-count budgeting**: users could game the daily cap with
   a few 16K-token calls. The cap counted requests, not tokens.
3. **Output format drift**: `OutputFormat` was a plain string. Typos
   like `'json-array'` (instead of `'json_array'`) landed silently in
   trace logs.

**Why the fix works**
- Hybrid search runs semantic + keyword **in parallel** and fuses via
  Reciprocal Rank Fusion (`RRF_K=60`). Chunks both retrievers rank
  highly shoot to the top.
- `check_and_charge_tokens()` / `settle_tokens()` pre-charges estimated
  tokens and settles against actual usage. A single 16K-token call now
  consumes 16K tokens of the daily budget, not 1 request.
- `OutputFormat = Literal['text', 'json', 'json_array']` — typos caught
  at import time.

**Regression red-flag**
- Short-circuiting hybrid search to "semantic first, keyword if empty."
- Any new budget enforcement that counts requests instead of tokens.
- Adding a new output format as a string literal instead of extending
  the `Literal`.

## P3.3 — Redis-backed memory-book checkpoints + DB-as-truth

**Locations**
- `packages/server/app/services/memory_book/checkpoint.py:1`, `:39`
- `packages/server/app/services/memory_book/pipeline.py:110`, `:167`, `:347`
- `packages/server/app/services/agent_service.py:54`

**What went wrong**
Memory-book generation is a multi-step pipeline (one LLM call per
section). If the process died mid-run (OOM, deploy, restart), sections
that completed but never made it to DB were lost. Next run re-attempted
**all** sections — under rate limits, this meant 5+ minutes of
redundant LLM calls per recovery.

**Why the fix works**
- Each section persists to Redis the moment it completes (TTL=1 hour).
- On next run, the pipeline reads checkpoints first and treats present
  sections as "already succeeded."
- After DB write succeeds, checkpoints are cleared.
- DB remains source of truth; Redis is purely an optimization.
- 1-hour TTL outlasts any single run + restart cycle but doesn't
  linger indefinitely.

**Regression red-flag**
- Treating checkpoint presence as authoritative without verifying
  against DB on final read.
- Skipping checkpoint cleanup after DB write (causes unbounded Redis
  growth).
- Bumping TTL past 24 hours (stale checkpoints survive deploy cycles
  they shouldn't).

## P3.4 — Per-section context budgeting with base prompt pinned

**Locations**
- `packages/server/app/services/companion/context_prompts.py:246`, `:306`, `:320`

**What went wrong**
All optional context sections (extra_context, RAG chunks, memory summary)
were concatenated and truncated **wholesale**. If budget was tight, ALL
of extra_context AND ALL of RAG got dropped while a giant memory_summary
stayed intact. No prioritization — high-signal content disappeared
entirely instead of being trimmed.

**Why the fix works**
- Optional sections ranked by signal density.
- Budgeted per-section in priority order, not concatenated.
- Base system prompt pinned BEFORE optional sections — role/task/format
  is never dropped.
- Persona text wrapped in XML-style tags (`<persona>...</persona>`) for
  attribution so the model treats it distinctly from role description.

**Regression red-flag**
- Concatenating optional sections before budgeting.
- Letting any optional section grow without a per-section cap.
- Dropping the base system prompt when budget is tight (ship a stub
  persona instead).

## P3.5 — Enum-vs-string status comparison silently disabled the completed-book RAG unfilter

**Locations**
- `packages/server/app/services/rag/context.py:47` (fixed)
- `packages/server/app/services/rag/cross_book.py:38` (caught pre-ship during Phase 2 Research-agent work)

**What went wrong**
``Book.status`` is declared as ``Enum(BookStatus, values_callable=...)``;
rows loaded through the ORM come back as **enum members**, not strings.
The spoiler gate compared ``book.status == 'completed'`` — in Python,
``BookStatus.completed == 'completed'`` is ``False``, so the check could
never fire. Every "completed" book stayed spoiler-capped at
``current_segment`` forever, contradicting the documented contract
("Completed books have no filter"). Discovered when the Phase 2
Research agent's cross-book search returned empty for a seeded
completed book whose needle chapter sat past ``current_segment``.

**Why the fix works**
- Python-side comparisons use the enum member:
  ``book.status == BookStatus.completed`` (the pattern
  ``_session_book_progress.py:34`` already used).
- SQL-side ``.where(Book.status == 'completed')`` is NOT affected — the
  Enum type's bind processor converts value strings, so those keep
  working.
- Regression test pins both layers: a completed book with a needle
  chunk at chapter 9 and ``current_segment=1`` must be retrievable
  (``tests/test_research_agent.py::test_completed_book_has_no_chapter_filter``).

**Regression red-flag**
- Any Python-side ``book.status == '<string>'`` comparison (grep the
  services tree when touching status logic).
- Tests that seed status but never exercise a code path where the enum
  value matters past the SQL layer.
